      38             : /// A ustring is an alternative to char* or std::string for storing
      39             : /// strings, in which the character sequence is unique (allowing many
      40             : /// speed advantages for assignment, equality testing, and inequality
      41             : /// testing).
      42             : ///
      43             : /// The implementation is that behind the scenes there is a hash set of
      44             : /// allocated strings, so the characters of each string are unique.  A
      45             : /// ustring itself is a pointer to the characters of one of these canonical
      46             : /// strings.  Therefore, assignment and equality testing is just a single
      47             : /// 32- or 64-bit int operation, the only mutex is when a ustring is
      48             : /// created from raw characters, and the only malloc is the first time
      49             : /// each canonical ustring is created.
      50             : ///
      51             : /// The internal table also contains a std::string version and the length
      52             : /// of the string, so converting a ustring to a std::string (via
      53             : /// ustring::string()) or querying the number of characters (via
      54             : /// ustring::size() or ustring::length()) is extremely inexpensive, and does
      55             : /// not involve creation/allocation of a new std::string or a call to
      56             : /// strlen.
      57             : ///
      58             : /// We try very hard to completely mimic the API of std::string,
      59             : /// including all the constructors, comparisons, iterations, etc.  Of
      60             : /// course, the characters of a ustring are non-modifiable, so we do not
      61             : /// replicate any of the non-const methods of std::string.  But in most
      62             : /// other ways it looks and acts like a std::string and so most templated
      63             : /// algorithms that would work on a "const std::string &" will also work
      64             : /// on a ustring.
      65             : ///
      66             : /// Note that like a `char*`, but unlike a `std::string`, a ustring is not
      67             : /// allowed to contain any embedded NUL ('\0') characters. When constructing
      68             : /// ustrings from a std::string or a string_view, the contents will be
      69             : /// truncated at the point of any NUL character. This is done to ensure that
      70             : /// ustring::c_str() refers to the same C-style character sequence as the
      71             : /// ustring itself or ustring::string().
      72             : ///
      73             : /// Usage guidelines:
      74             : ///
      75             : /// Compared to standard strings, ustrings have several advantages:
      76             : ///
      77             : ///   - Each individual ustring is very small -- in fact, we guarantee that
      78             : ///     a ustring is the same size and memory layout as an ordinary char*.
      79             : ///   - Storage is frugal, since there is only one allocated copy of each
      80             : ///     unique character sequence, throughout the lifetime of the program.
      81             : ///   - Assignment from one ustring to another is just copy of the pointer;
      82             : ///     no allocation, no character copying, no reference counting.
      83             : ///   - Equality testing (do the strings contain the same characters) is
      84             : ///     a single operation, the comparison of the pointer.
      85             : ///   - Memory allocation only occurs when a new ustring is constructed from
      86             : ///     raw characters the FIRST time -- subsequent constructions of the
      87             : ///     same string just finds it in the canonical string set, but doesn't
      88             : ///     need to allocate new storage.  Destruction of a ustring is trivial,
      89             : ///     there is no de-allocation because the canonical version stays in
      90             : ///     the set.  Also, therefore, no user code mistake can lead to
      91             : ///     memory leaks.
      92             : ///
      93             : /// But there are some problems, too.  Canonical strings are never freed
      94             : /// from the table.  So in some sense all the strings "leak", but they
      95             : /// only leak one copy for each unique string that the program ever comes
      96             : /// across.  Also, creation of unique strings from raw characters is more
      97             : /// expensive than for standard strings, due to hashing, table queries,
      98             : /// and other overhead.
      99             : ///
     100             : /// On the whole, ustrings are a really great string representation
     101             : ///   - if you tend to have (relatively) few unique strings, but many
     102             : ///     copies of those strings;
     103             : ///   - if the creation of strings from raw characters is relatively
     104             : ///     rare compared to copying or comparing to existing strings;
     105             : ///   - if you tend to make the same strings over and over again, and
     106             : ///     if it's relatively rare that a single unique character sequence
     107             : ///     is used only once in the entire lifetime of the program;
     108             : ///   - if your most common string operations are assignment and equality
     109             : ///     testing and you want them to be as fast as possible;
     110             : ///   - if you are doing relatively little character-by-character assembly
     111             : ///     of strings, string concatenation, or other "string manipulation"
     112             : ///     (other than equality testing).
     113             : ///
     114             : /// ustrings are not so hot
     115             : ///   - if your program tends to have very few copies of each character
     116             : ///     sequence over the entire lifetime of the program;
     117             : ///   - if your program tends to generate a huge variety of unique
     118             : ///     strings over its lifetime, each of which is used only a short
     119             : ///     time and then discarded, never to be needed again;
     120             : ///   - if you don't need to do a lot of string assignment or equality
