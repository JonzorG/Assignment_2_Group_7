      36             : /// \class UsdGeomPointInstancer
      37             : ///
      38             : /// Encodes vectorized instancing of multiple, potentially
      39             : /// animated, prototypes (object/instance masters), which can be arbitrary
      40             : /// prims/subtrees on a UsdStage.
      41             : /// 
      42             : /// PointInstancer is a "multi instancer", as it allows multiple prototypes
      43             : /// to be scattered among its "points".  We use a UsdRelationship
      44             : /// \em prototypes to identify and order all of the possible prototypes, by
      45             : /// targeting the root prim of each prototype.  The ordering imparted by
      46             : /// relationships associates a zero-based integer with each prototype, and
      47             : /// it is these integers we use to identify the prototype of each instance,
      48             : /// compactly, and allowing prototypes to be swapped out without needing to
      49             : /// reauthor all of the per-instance data.
      50             : /// 
      51             : /// The PointInstancer schema is designed to scale to billions of instances,
      52             : /// which motivates the choice to split the per-instance transformation into
      53             : /// position, (quaternion) orientation, and scales, rather than a
      54             : /// 4x4 matrix per-instance.  In addition to requiring fewer bytes even if
      55             : /// all elements are authored (32 bytes vs 64 for a single-precision 4x4
      56             : /// matrix), we can also be selective about which attributes need to animate
      57             : /// over time, for substantial data reduction in many cases.
      58             : /// 
      59             : /// Note that PointInstancer is \em not a Gprim, since it is not a graphical
      60             : /// primitive by any stretch of the imagination. It \em is, however,
      61             : /// Boundable, since we will sometimes want to treat the entire PointInstancer
      62             : /// similarly to a procedural, from the perspective of inclusion or framing.
      63             : /// 
      64             : /// \section UsdGeomPointInstancer_varyingTopo Varying Instance Identity over Time
      65             : /// 
      66             : /// PointInstancers originating from simulations often have the characteristic
      67             : /// that points/instances are "born", move around for some time period, and then
      68             : /// die (or leave the area of interest). In such cases, billions of instances
      69             : /// may be birthed over time, while at any \em specific time, only a much
      70             : /// smaller number are actually alive.  To encode this situation efficiently,
      71             : /// the simulator may re-use indices in the instance arrays, when a particle
      72             : /// dies, its index will be taken over by a new particle that may be birthed in
      73             : /// a much different location.  This presents challenges both for 
      74             : /// identity-tracking, and for motion-blur.
      75             : /// 
      76             : /// We facilitate identity tracking by providing an optional, animatable
      77             : /// \em ids attribute, that specifies the 64 bit integer ID of the particle
      78             : /// at each index, at each point in time.  If the simulator keeps monotonically
      79             : /// increasing a particle-count each time a new particle is birthed, it will
      80             : /// serve perfectly as particle \em ids.
      81             : /// 
      82             : /// We facilitate motion blur for varying-topology particle streams by
      83             : /// optionally allowing per-instance \em velocities and \em angularVelocities
      84             : /// to be authored.  If instance transforms are requested at a time between
      85             : /// samples and either of the velocity attributes is authored, then we will
      86             : /// not attempt to interpolate samples of \em positions or \em orientations.
      87             : /// If not authored, and the bracketing samples have the same length, then we
      88             : /// will interpolate.
      89             : /// 
      90             : /// \section UsdGeomPointInstancer_transform Computing an Instance Transform
      91             : /// 
      92             : /// Each instance's transformation is a combination of the SRT affine transform
      93             : /// described by its scale, orientation, and position, applied \em after
      94             : /// (i.e. less locally than) the local to parent transformation computed at 
      95             : /// the root of the prototype it is instancing. 
      96             : /// 
      97             : /// To understand the computation of the instance transform, in order to put
      98             : /// an instance of a PointInstancer into the space of the PointInstancer's 
      99             : /// parent prim we do the following:
     100             : /// 
     101             : /// 1. Apply (most locally) the authored local to parent transformation for 
     102             : /// <em>prototypes[protoIndices[i]]</em>
     103             : /// 2. If *scales* is authored, next apply the scaling matrix from *scales[i]*
     104             : /// 3. If *orientations* is authored: **if *angularVelocities* is authored**, 
     105             : /// first multiply *orientations[i]* by the unit quaternion derived by scaling 
     106             : /// *angularVelocities[i]* by the \ref UsdGeom_PITimeScaling "time differential" 
     107             : /// from the left-bracketing timeSample for *orientation* to the requested 
     108             : /// evaluation time *t*, storing the result in *R*, **else** assign *R* 
     109             : /// directly from *orientations[i]*.  Apply the rotation matrix derived 
     110             : /// from *R*.
     111             : /// 4. Apply the translation derived from *positions[i]*. If *velocities* is 
     112             : /// authored, apply the translation deriving from *velocities[i]* scaled by 
     113             : /// the time differential from the left-bracketing timeSample for *positions* 
     114             : /// to the requested evaluation time *t*.
     115             : /// 5. Least locally, apply the transformation authored on the PointInstancer 
     116             : /// prim itself (or the UsdGeomImageable::ComputeLocalToWorldTransform() of the 
     117             : /// PointInstancer to put the instance directly into world space)
     118             : /// 
     119             : /// If neither *velocities* nor *angularVelocities* are authored, we fallback to
     120             : /// standard position and orientation computation logic (using linear
     121             : /// interpolation between timeSamples) as described by
     122             : /// \ref UsdGeom_VelocityInterpolation .
     123             : /// 
     124             : /// \anchor UsdGeom_PITimeScaling
     125             : /// <b>Scaling Velocities for Interpolation</b>
     126             : /// 
     127             : /// When computing time-differentials by which to apply velocity or
     128             : /// angularVelocity to positions or orientations, we must scale by
     129             : /// ( 1.0 / UsdStage::GetTimeCodesPerSecond() ), because velocities are recorded
     130             : /// in units/second, while we are interpolating in UsdTimeCode ordinates.
     131             : /// 
     132             : /// We provide both high and low-level API's for dealing with the
     133             : /// transformation as a matrix, both will compute the instance matrices using
     134             : /// multiple threads; the low-level API allows the client to cache unvarying
     135             : /// inputs so that they need not be read duplicately when computing over
     136             : /// time.
     137             : /// 
     138             : /// See also \ref UsdGeom_VelocityInterpolation .
     139             : /// 
     140             : /// \section UsdGeomPointInstancer_primvars Primvars on PointInstancer
     141             : /// 
     142             : /// \ref UsdGeomPrimvar "Primvars" authored on a PointInstancer prim should
     143             : /// always be applied to each instance with \em constant interpolation at
     144             : /// the root of the instance.  When you are authoring primvars on a 
     145             : /// PointInstancer, think about it as if you were authoring them on a 
     146             : /// point-cloud (e.g. a UsdGeomPoints gprim).  The same 
     147             : /// <A HREF="https://renderman.pixar.com/resources/RenderMan_20/appnote.22.html#classSpecifiers">interpolation rules for points</A> apply here, substituting
     148             : /// "instance" for "point".
     149             : /// 
     150             : /// In other words, the (constant) value extracted for each instance
     151             : /// from the authored primvar value depends on the authored \em interpolation
     152             : /// and \em elementSize of the primvar, as follows:
     153             : /// \li <b>constant</b> or <b>uniform</b> : the entire authored value of the
     154             : /// primvar should be applied exactly to each instance.
     155             : /// \li <b>varying</b>, <b>vertex</b>, or <b>faceVarying</b>: the first
     156             : /// \em elementSize elements of the authored primvar array should be assigned to
     157             : /// instance zero, the second \em elementSize elements should be assigned to
     158             : /// instance one, and so forth.
     159             : /// 
     160             : /// 
     161             : /// \section UsdGeomPointInstancer_masking Masking Instances: "Deactivating" and Invising
     162             : /// 
     163             : /// Often a PointInstancer is created "upstream" in a graphics pipeline, and
     164             : /// the needs of "downstream" clients necessitate eliminating some of the 
     165             : /// instances from further consideration.  Accomplishing this pruning by 
     166             : /// re-authoring all of the per-instance attributes is not very attractive,
     167             : /// since it may mean destructively editing a large quantity of data.  We
     168             : /// therefore provide means of "masking" instances by ID, such that the 
     169             : /// instance data is unmolested, but per-instance transform and primvar data
     170             : /// can be retrieved with the no-longer-desired instances eliminated from the
     171             : /// (smaller) arrays.  PointInstancer allows two independent means of masking
     172             : /// instances by ID, each with different features that meet the needs of
     173             : /// various clients in a pipeline.  Both pruning features' lists of ID's are
     174             : /// combined to produce the mask returned by ComputeMaskAtTime().
     175             : /// 
     176             : /// \note If a PointInstancer has no authored \em ids attribute, the masking
     177             : /// features will still be available, with the integers specifying element
     178             : /// position in the \em protoIndices array rather than ID.
     179             : /// 
     180             : /// \subsection UsdGeomPointInstancer_inactiveIds InactiveIds: List-edited, Unvarying Masking
     181             : /// 
     182             : /// The first masking feature encodes a list of IDs in a list-editable metadatum
     183             : /// called \em inactiveIds, which, although it does not have any similar 
     184             : /// impact to stage population as \ref UsdPrim::SetActive() "prim activation",
     185             : /// it shares with that feature that its application is uniform over all time.
     186             : /// Because it is list-editable, we can \em sparsely add and remove instances
     187             : /// from it in many layers.
     188             : /// 
     189             : /// This sparse application pattern makes \em inactiveIds a good choice when
     190             : /// further downstream clients may need to reverse masking decisions made
     191             : /// upstream, in a manner that is robust to many kinds of future changes to
     192             : /// the upstream data.
     193             : /// 
     194             : /// See ActivateId(), ActivateIds(), DeactivateId(), DeactivateIds(), 
     195             : /// ActivateAllIds()
     196             : /// 
     197             : /// \subsection UsdGeomPointInstancer_invisibleIds invisibleIds: Animatable Masking
     198             : /// 
     199             : /// The second masking feature encodes a list of IDs in a time-varying
     200             : /// Int64Array-valued UsdAttribute called \em invisibleIds , since it shares
     201             : /// with \ref UsdGeomImageable::GetVisibilityAttr() "Imageable visibility"
     202             : /// the ability to animate object visibility.
     203             : /// 
     204             : /// Unlike \em inactiveIds, overriding a set of opinions for \em invisibleIds
     205             : /// is not at all straightforward, because one will, in general need to
     206             : /// reauthor (in the overriding layer) **all** timeSamples for the attribute
     207             : /// just to change one Id's visibility state, so it cannot be authored
     208             : /// sparsely.  But it can be a very useful tool for situations like encoding
     209             : /// pre-computed camera-frustum culling of geometry when either or both of
     210             : /// the instances or the camera is animated.
     211             : /// 
     212             : /// See VisId(), VisIds(), InvisId(), InvisIds(), VisAllIds()
     213             : /// 
     214             : /// \section UsdGeomPointInstancer_protoProcessing Processing and Not Processing Prototypes
     215             : /// 
     216             : /// Any prim in the scenegraph can be targeted as a prototype by the
     217             : /// \em prototypes relationship.  We do not, however, provide a specific
     218             : /// mechanism for identifying prototypes as geometry that should not be drawn
     219             : /// (or processed) in their own, local spaces in the scenegraph.  We
     220             : /// encourage organizing all prototypes as children of the PointInstancer
     221             : /// prim that consumes them, and pruning "raw" processing and drawing
     222             : /// traversals when they encounter a PointInstancer prim; this is what the
     223             : /// UsdGeomBBoxCache and UsdImaging engines do.
     224             : /// 
     225             : /// There \em is a pattern one can deploy for organizing the prototypes such
     226             : /// that they will automatically be skipped by basic UsdPrim::GetChildren() or
     227             : /// UsdPrimRange traversals.  Usd prims each have a \ref Usd_PrimSpecifiers
     228             : /// "specifier" of "def", "over", or "class".  The default traversals skip over
     229             : /// prims that are "pure overs" or classes.  So to protect prototypes from all
     230             : /// generic traversals and processing, place them under a prim that is a "class"
     231             : /// or "over". "class" is recommended , while "over" should be used when
     232             : /// backwards compatibility with older versions of USD is needed. For example,
     233             : /// \code
     234             : /// 01 def PointInstancer "Crowd_Mid"
     235             : /// 02 {
     236             : /// 03     rel prototypes = [ </Crowd_Mid/Prototypes/MaleThin_Business>, </Crowd_Mid/OtherPrototypes/MaleThin_Casual> ]
     237             : /// 04     
     238             : /// 05     over "Prototypes" 
     239             : /// 06     {
     240             : /// 07          def "MaleThin_Business" (
     241             : /// 08              references = [@MaleGroupA/usd/MaleGroupA.usd@</MaleGroupA>]
     242             : /// 09              variants = {
     243             : /// 10                  string modelingVariant = "Thin"
     244             : /// 11                  string costumeVariant = "BusinessAttire"
     245             : /// 12              }
     246             : /// 13          )
     247             : /// 14          { ... }
     248             : /// 15     }
     249             : /// 16
     250             : /// 17     class "OtherPrototypes"
     251             : /// 18     {
     252             : /// 19          def "MaleThin_Casual"
     253             : /// 20          ...
     254             : /// 21     }
     255             : /// 22 }
     256             : /// \endcode
