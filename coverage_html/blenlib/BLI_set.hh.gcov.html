       7             : /** \file
       8             :  * \ingroup bli
       9             :  *
      10             :  * A `Set<Key>` is an unordered container for unique elements of type `Key`. It is
      11             :  * designed to be a more convenient and efficient replacement for `std::unordered_set`. All core
      12             :  * operations (add, remove and contains) can be done in O(1) amortized expected time.
      13             :  *
      14             :  * In most cases, your default choice for a hash set in Blender should be `Set`.
      15             :  *
      16             :  * Set is implemented using open addressing in a slot array with a power-of-two size.
      17             :  * Every slot is in one of three states: empty, occupied or removed. If a slot is occupied, it
      18             :  * contains an instance of the key type.
      19             :  *
      20             :  * Bench-marking and comparing hash tables is hard, because many factors influence the result. The
      21             :  * performance of a hash table depends on the combination of the hash function, probing strategy,
      22             :  * max load factor, key type, slot type and the data distribution. This implementation is designed
      23             :  * to be relatively fast by default in all cases. However, it also offers many customization
      24             :  * points that allow it to be optimized for a specific use case.
      25             :  *
      26             :  * A rudimentary benchmark can be found in `BLI_set_test.cc`. The results of that benchmark are
      27             :  * there as well. The numbers show that in this specific case #Set outperforms
      28             :  * #std::unordered_set consistently by a good amount.
      29             :  *
      30             :  * Some noteworthy information:
      31             :  * - Key must be a movable type.
      32             :  * - Pointers to keys might be invalidated when the set is changed or moved.
      33             :  * - The hash function can be customized. See BLI_hash.hh for details.
      34             :  * - The probing strategy can be customized. See BLI_probing_stragies.hh for details.
      35             :  * - The slot type can be customized. See BLI_set_slots.hh for details.
      36             :  * - Small buffer optimization is enabled by default, if the key is not too large.
      37             :  * - The methods `add_new` and `remove_contained` should be used instead of `add` and `remove`
      38             :  *   whenever appropriate. Assumptions and intention are described better this way.
      39             :  * - Lookups can be performed using types other than Key without conversion. For that use the
      40             :  *   methods ending with `_as`. The template parameters Hash and #IsEqual have to support the other
      41             :  *   key type. This can greatly improve performance when the set contains strings.
      42             :  * - The default constructor is cheap, even when a large #InlineBufferCapacity is used. A large
      43             :  *   slot array will only be initialized when the first key is added.
      44             :  * - The `print_stats` method can be used to get information about the distribution of keys and
      45             :  *   memory usage of the set.
      46             :  * - The method names don't follow the std::unordered_set names in many cases. Searching for such
      47             :  *   names in this file will usually let you discover the new name.
      48             :  *
      49             :  * Possible Improvements:
      50             :  * - Use a branch-less loop over slots in grow function (measured ~10% performance improvement when
      51             :  *   the distribution of occupied slots is sufficiently random).
      52             :  * - Support max load factor customization.
      53             :  * - Improve performance with large data sets through software prefetching. I got fairly
      54             :  *   significant improvements in simple tests (~30% faster). It still needs to be investigated how
      55             :  *   to make a nice interface for this functionality.
      56             :  */
