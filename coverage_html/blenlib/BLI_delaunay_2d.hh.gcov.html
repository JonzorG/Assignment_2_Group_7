      22             : /**
      23             :  * Interface for Constrained Delaunay Triangulation (CDT) in 2D.
      24             :  *
      25             :  * The input is a set of vertices, edges between those vertices,
      26             :  * and faces using those vertices.
      27             :  * Those inputs are called "constraints". The output must contain
      28             :  * those constraints, or at least edges, points, and vertices that
      29             :  * may be pieced together to form the constraints. Part of the
      30             :  * work of doing the CDT is to detect intersections and mergers
      31             :  * among the input elements, so these routines are also useful
      32             :  * for doing 2D intersection.
      33             :  *
      34             :  * The output is a triangulation of the plane that includes the
      35             :  * constraints in the above sense, and also satisfies the
      36             :  * "Delaunay condition" as modified to take into account that
      37             :  * the constraints must be there: for every non-constrained edge
      38             :  * in the output, there is a circle through the endpoints that
      39             :  * does not contain any of the vertices directly connected to
      40             :  * those endpoints. What this means in practice is that as
      41             :  * much as possible the triangles look "nice" -- not too long
      42             :  * and skinny.
      43             :  *
      44             :  * Optionally, the output can be a subset of the triangulation
      45             :  * (but still containing all of the constraints), to get the
      46             :  * effect of 2D intersection.
      47             :  *
      48             :  * The underlying method is incremental, but we need to know
      49             :  * beforehand a bounding box for all of the constraints.
      50             :  * This code can be extended in the future to allow for
      51             :  * deletion of constraints, if there is a use in Blender
      52             :  * for dynamically maintaining a triangulation.
      53             :  */

     122             : /**
     123             :  * Input to Constrained Delaunay Triangulation.
     124             :  * Input vertex coordinates are stored in `vert`. For the rest of the input,
     125             :  * vertices are referred to by indices into that array.
     126             :  * Edges and Faces are optional. If provided, they will
     127             :  * appear in the output triangulation ("constraints").
     128             :  * One can provide faces and not edges -- the edges
     129             :  * implied by the faces will be inferred.
     130             :  *
     131             :  * The edges are given by pairs of vertex indices.
     132             :  * The faces are given as groups of vertex indices, in counterclockwise order
     133             :  * when original face ids are required (#CDT_ORIG_FACES) or for #CDT_CONSTRAINTS_VALID_BMESH.
     134             :  * `*_NONZERO` outputs use the orientation as the winding, even-odd filling ignores it.
     135             :  *
     136             :  * The edges implied by the faces are automatically added
     137             :  * and need not be put in the edges array, which is intended
     138             :  * as a way to specify edges that are not part of any face.
     139             :  *
     140             :  * Some notes about some special cases and how they are handled:
     141             :  * - Input faces can have any number of vertices greater than 2. Depending
     142             :  *   on the output option, ngons may be triangulated or they may remain
     143             :  *   as ngons.
     144             :  * - Input faces may have repeated vertices. Output faces will not,
     145             :  *   except when the CDT_CONSTRAINTS output option is used.
     146             :  * - Input faces may have edges that self-intersect, but currently the labeling
     147             :  *   of which output faces have which input faces may not be done correctly,
     148             :  *   since the labeling relies on the inside being on the left of edges
     149             :  *   as one traverses the face. Output faces will not self-intersect.
     150             :  * - Input edges, including those implied by the input faces, may have
     151             :  *   zero-length or near-zero-length edges (nearness as determined by epsilon),
     152             :  *   but those edges will not be in the output.
     153             :  * - Input edges (including face edges) can overlap or nearly overlap each other.
     154             :  *   The output edges will not overlap, but instead be divided into as many
     155             :  *   edges as necessary to represent each overlap regime.
     156             :  * - Input vertices may be coincide with, or nearly coincide with (as determined
     157             :  *   by epsilon) other input vertices. Only one representative will survive
     158             :  *   in the output. If an input vertex is within epsilon of an edge (including
     159             :  *   an added triangulation edge), it will be snapped to that edge, so the
     160             :  *   output coordinates may not exactly match the input coordinates in all cases.
     161             :  * - Wire edges (those not part of faces) and isolated vertices are allowed in
     162             :  *   the input. If they are inside faces, they will be incorporated into the
     163             :  *   triangulation of those faces.
     164             :  *
     165             :  * Epsilon is used for "is it near enough" distance calculations.
     166             :  * If zero is supplied for epsilon, an internal value of 1e-8 used
     167             :  * instead, since this code will not work correctly if it is not allowed
     168             :  * to merge "too near" vertices.
     169             :  *
     170             :  * Normally the output will not contain mappings from outputs to inputs,
     171             :  * which leads to faster execution.
