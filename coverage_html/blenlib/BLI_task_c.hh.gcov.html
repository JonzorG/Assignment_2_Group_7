     328             : /** \name Task Isolation
     329             :  *
     330             :  * Task isolation helps avoid unexpected task scheduling decisions that can lead to bugs if wrong
     331             :  * assumptions were made. Typically that happens when doing "nested threading", i.e. one thread
     332             :  * schedules a bunch of main-tasks and those spawn new sub-tasks.
     333             :  *
     334             :  * What can happen is that when a main-task waits for its sub-tasks to complete on other threads,
     335             :  * another main-task is scheduled within the already running main-task. Generally, this is good,
     336             :  * because it leads to better performance. However, sometimes code (often unintentionally) makes
     337             :  * the assumption that at most one main-task runs on a thread at a time.
     338             :  *
     339             :  * The bugs often show themselves in two ways:
     340             :  * - Deadlock, when a main-task holds a mutex while waiting for its sub-tasks to complete.
     341             :  * - Data corruption, when a main-task makes wrong assumptions about a thread-local variable.
     342             :  *
     343             :  * Task isolation can avoid these bugs by making sure that a main-task does not start executing
     344             :  * another main-task while waiting for its sub-tasks. More precisely, a function that runs in an
     345             :  * isolated region is only allowed to run sub-tasks that were spawned in the same isolated region.
     346             :  *
     347             :  * Unfortunately, incorrect use of task isolation can lead to deadlocks itself. This can happen
     348             :  * when threading primitives are used that separate spawning tasks from executing them. The problem
     349             :  * occurs when a task is spawned in one isolated region while the tasks are waited for in another
     350             :  * isolated region. In this setup, the thread that is waiting for the spawned tasks to complete
     351             :  * cannot run the tasks itself. On a single thread, that causes a deadlock already. When there are
     352             :  * multiple threads, another thread will typically run the task and avoid the deadlock. However, if
     353             :  * this situation happens on all threads at the same time, all threads will deadlock. This happened
     354             :  * in #88598.
