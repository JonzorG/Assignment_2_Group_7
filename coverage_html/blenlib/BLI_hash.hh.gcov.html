      19             :  *
      20             :  * Hash table implementations like Set support heterogeneous key lookups. That means that
      21             :  * one can do a lookup with a key of type A in a hash table that stores keys of type B. This is
      22             :  * commonly done when B is std::string, because the conversion from e.g. a #StringRef to
      23             :  * std::string can be costly and is unnecessary. To make this work, values of type A and B that
      24             :  * compare equal have to have the same hash value. This is achieved by defining potentially
      25             :  * multiple `operator()` in a specialization of #DefaultHash. All those methods have to compute the
      26             :  * same hash for values that compare equal.
      27             :  *
      28             :  * The computed hash is an unsigned 64 bit integer. Ideally, the hash function would generate
      29             :  * uniformly random hash values for a set of keys. However, in many cases trivial hash functions
      30             :  * are faster and produce a good enough distribution. In general it is better when more information
      31             :  * is in the lower bits of the hash. By choosing a good probing strategy, the effects of a bad hash
      32             :  * function are less noticeable though. In this context a good probing strategy is one that takes
      33             :  * all bits of the hash into account eventually. One has to check on a case by case basis to see if
      34             :  * a better but more expensive or trivial hash function works better.
      35             :  *
      36             :  * There are three main ways to provide a hash table implementation with a custom hash function.
      37             :  *
