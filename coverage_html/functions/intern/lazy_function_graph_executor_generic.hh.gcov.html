       8             :  * This file implements the evaluation of a lazy-function graph. It's main objectives are:
       9             :  * - Only compute values that are actually used.
      10             :  * - Stay single threaded when nodes are executed quickly.
      11             :  * - Allow spreading the work over an arbitrary number of threads efficiently.
      12             :  *
      13             :  * This executor makes use of `FN_lazy_threading.hh` to enable multi-threading only when it seems
      14             :  * beneficial. It operates in two modes: single- and multi-threaded. The use of a task pool and
      15             :  * locks is avoided in single-threaded mode. Once multi-threading is enabled the executor starts
      16             :  * using both. It is not possible to switch back from multi-threaded to single-threaded mode.
      17             :  *
      18             :  * The multi-threading design implemented in this executor requires *no* main thread that
      19             :  * coordinates everything. Instead, one thread will trigger some initial work and then many threads
      20             :  * coordinate themselves in a distributed fashion. In an ideal situation, every thread ends up
      21             :  * processing a separate part of the graph which results in less communication overhead. The way
      22             :  * TBB schedules tasks helps with that: a thread will next process the task that it added to a task
      23             :  * pool just before.
      24             :  *
      25             :  * Communication between threads is synchronized by using a mutex in every node. When a thread
      26             :  * wants to access the state of a node, its mutex has to be locked first (with some documented
      27             :  * exceptions). The assumption here is that most nodes are only ever touched by a single thread and
      28             :  * therefore the lock contention is reduced the more nodes there are.
      29             :  *
      30             :  * Similar to how a #LazyFunction can be thought of as a state machine (see `FN_lazy_function.hh`),
      31             :  * each node can also be thought of as a state machine. The state of a node contains the evaluation
      32             :  * state of its inputs and outputs. Every time a node is executed, it has to advance its state in
      33             :  * some way (e.g. it requests a new input or computes a new output).
      34             :  *
      35             :  * When a node is executed it may send notifications to other nodes which may in turn schedule
      36             :  * those nodes. For example, when the current node has computed one of its outputs, then the
      37             :  * computed value is forwarded to all linked inputs, changing their node states in the process. If
      38             :  * this input was the last missing required input, the node will be scheduled that it is executed
      39             :  * next.
      40             :  *
      41             :  * When all tasks are completed, the executor gives back control to the caller which may later
      42             :  * provide new inputs to the graph which in turn leads to new nodes being scheduled and the process
      43             :  * starts again.
      44             :  */
